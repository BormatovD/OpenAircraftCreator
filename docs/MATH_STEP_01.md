# Математика, шаг 01: одинаковые условия калибровки и рабочего расчёта

Дата: 11 ноября 2026 года. База: `366b4d11b12fa477c8498d0a4230fb2a08c8ab0b` —
`Apply complete compact UI and vertical lever layout`.

## Результат

Устранена потеря параметров двигателя при подборе крейсерского удельного расхода топлива (TSFC).
Теперь обратная задача и повторный прямой расчёт используют одинаковые условия двигателя и миссии.
На штатных калибровочных точках A320ceo и A320neo численный эффект равен нулю:
раньше срабатывает ограничение по подъёмной силе, поэтому потеря ограничения тяги здесь не меняла эшелоны.
Эта ошибка **не объясняет нынешние проценты расхождений с источниками**.

Опорный TSFC рабочей модели остаётся **0,586 lb/(lbf·h)**. Калибровочный скрипт выдаёт кандидата
для отдельного инженерного решения; автоматического изменения контекста нет.

## Что изменено и почему

В [calibrateTsfc](../src/calibrate.ts) раньше в миссию передавался только `{ tsfcCruise }`.
Рабочий путь [engineStateFor](../src/evaluate.ts) передаёт также суммарную взлётную тягу,
опорный Мах и двухконтурность. Тяга влияет на доступные эшелоны, следовательно,
при активном тяговом ограничении обратная задача могла подбирать TSFC для другого профиля полёта.

Теперь `calibrateTsfc` требует явный `fixedEngine: Omit<EngineState, "tsfcCruise">`.
Единая функция расчёта строк сохраняет эти поля и заменяет только подбираемый TSFC:

```ts
compareAircraft(ac, aero, { ...fixedEngine, tsfcCruise: candidate }, assumptions, density);
```

Этот путь используется и внутри оптимизации, и при формировании результата. В прежних тестах
идеализированной модели явно передаётся `{}`: отсутствие ограничения тяги там является выбранным условием.
Алгоритм поиска и его 40 итераций не изменены. Дискретные переключения эшелонов остаются частью миссии;
строгая унимодальность целевой функции не утверждается.

[Скрипт A320](../scripts/calibrate-a320.ts) получает условия через `assumptionsFor` и `engineStateFor`.
Проверка CEO с wingtip fences сохраняет состояние своего двигателя и использует TSFC, подобранный по Sharklet.
В JSON-отчёте появились состояние двигателя, назначение каждого подбора и действующая опора модели.

Самостоятельный подбор NEO помечен как **диагностика**. Рабочий прогноз LEAP по-прежнему получается
через модель цикла относительно CEO. Подобранный эффективный TSFC NEO нельзя записывать в опору CEO
и затем повторно умножать на отношение циклов.

Поля `referenceMach` и `bypassRatio` сохранены для корректного контракта. Их отдельная численная
поправка по Маху сейчас отключена через `HOWE_MACH_TSFC = false`; этот шаг её не включает.

## Числа до и после

Здесь показаны результаты **подбора**, а не ошибки текущей рабочей модели при неизменной опоре 0,586.
Единица TSFC — lb/(lbf·h), RMS — среднеквадратичная относительная ошибка дальности.

| Набор | TSFC до | TSFC после | RMS до | RMS после |
| --- | ---: | ---: | ---: | ---: |
| A320ceo Sharklet, 8 точек | 0,5862666503 | 0,5862666503 | 0,625197% | 0,625197% |
| A320neo, диагностический подбор, 8 точек | 0,4897537096 | 0,4897537096 | 1,801680% | 1,801680% |

Повторный расчёт с полным состоянием двигателя точно совпадает со строками и RMS калибратора.
Проверка CEO fence с TSFC Sharklet после правки даёт RMS **0,913985%**.

Отдельно сопоставлен рабочий расчёт при опоре 0,586 на исходной базе и после изменения:

| Проверенная совокупность | Охват | Изменение |
| --- | ---: | --- |
| Payload/range: Airbus и Boeing | 499 точек, из них 78 Airbus и 421 Boeing | Все результаты совпали |
| Независимые контрольные точки крейсерского расхода | 247 точек | Все результаты совпали |
| Стандартная миссия доступных вариантов в интерфейсе | 9 полных результатов `Evaluation` | Все результаты совпали |

Два детерминированных JSON-снимка объёмом 460 166 байт совпали побайтно. Это проверка отсутствия
непредусмотренных изменений на указанном наборе, а не доказательство точности всей модели или всех комбинаций рычагов.
Численные расхождения из предыдущего инженерного HTML-разбора остаются актуальными.

## Проверка, которая обнаруживает прежнюю ошибку

Обычный A320 не чувствителен к этой ошибке, поэтому добавлена синтетическая обратная задача
в [calibration-context.test.ts](../test/calibration-context.test.ts).

Берём первую кривую A320ceo Sharklet, задаём **85% исходной располагаемой тяги**, то есть
204 170 Н суммарно, и известный TSFC **0,586**. Это искусственное условие численного теста,
оно не объявляется новым реальным исполнением A320. При этой тяге начальный допустимый эшелон — FL310;
без ограничения тяги — FL350. Оба расчёта находятся в допустимом высотном диапазоне модели.

Прямым расчётом получаем две синтетические дальности: **1760,390770617** и **3092,085510322 nm**.
Затем по ним восстанавливаем известный TSFC.

| Вариант обратной задачи | Найденный TSFC | RMS внутри подбора | RMS повторного расчёта с полным двигателем |
| --- | ---: | ---: | ---: |
| Прежнее поведение: поля двигателя потеряны | 0,5889800278 | 0,303590% | 0,613546% |
| Исправленный путь | 0,5860000002 | 4,38 × 10⁻⁸% | 4,38 × 10⁻⁸% |

Прежний путь ошибается в TSFC на **+0,5085%**. Новый тест проверяет и восстановление известного
параметра, и совпадение возвращённых строк с повторным расчётом. Поэтому исправить только итоговую
таблицу, оставив неправильную целевую функцию, недостаточно для прохождения теста.
Это проверка согласованности программы, а не независимая валидация физики по FCOM.

## Проверки и применение

- `npm test`: **141/141**, включая два новых теста.
- `npm run typecheck`: успешно.
- `npm run build`: успешно.
- `npm run calibrate`: успешно; отчёт — `out/calibration-a320.json`.
- Отрицательный контроль с намеренно потерянными полями воспроизводит ошибку из таблицы выше.
- Патч подготовлен как одно приращение к базе `366b4d1`; прежние FCOM и UI-пакеты повторно не нужны.

Патч применяется из корня проекта с сохранёнными изменениями исходников. Сначала проверить состояние:

```bash
git status --short
git log -1 --oneline
```

Для исходной базы ожидается `366b4d1 Apply complete compact UI and vertical lever layout`.
Если поверх неё уже есть собственные коммиты, предварительная проверка ниже покажет применимость патча.

```bash
oac_math_patch="$HOME/Downloads/OpenAircraftCreator-Math-Step-01-from-366b4d1.patch"
git apply --check --index "$oac_math_patch" && git am "$oac_math_patch"
```

При ошибке проверки не применять патч принудительно: нужны фактический `git status` и сообщение об ошибке.
После успешного применения выполнить `npm test`, `npm run typecheck` и `npm run calibrate`.
Для обновления офлайн-сборки выполнить `npm run build`.

## Документы: что уже есть и что искать

**Для этого шага новые документы не нужны. Для следующей работы с фазами A320 ISA0 тоже уже есть основа.**
В [CES FCOM](FCOM_AIRBUS_CES.md) извлечены **413 фазовых записей**: 241 climb, 136 holding, 36 descent;
отдельно сохранены 18 контрольных узлов крейсера. Применимость — A320-214 / CFM56-5B4/P SAC,
wingtip fences, ISA, normal A/C, anti-ice OFF. Это не универсальные таблицы для Sharklet и NEO.

В томе 3 нужны уже имеющиеся PDF-страницы: набор **1636/1637/1644**, ожидание **1825/1826**,
снижение **1845/1846**, крейсер **1707/1724**. Общая методика и резервы — том 2,
PDF **647, 654–657, 782–783**. Это номера PDF-страниц, а не номера разделов FCOM.

Кандидаты для A319/A321ceo и повышенных температур также уже есть в CES; требуется проверка
effectivity и извлечение. [HC-CLF](FCOM_HC_CLF.md) даёт отдельный A319-112/CFM56-5B6/P.
[737-800/CFM56-7B26](FCOM_BOEING_737_REVIEW.md) уже обеспечен LRC, holding и descent с топливом.
[Nordwind 757](FCOM_757_NORDWIND.md) даёт применимые LRC/holding для PW2037 обычного крыла, но не содержит RB211.

Дополнительные уточнения A320 полезны, но не блокируют первый диагностический шаг:

- В pure-descent таблице `WEIGHT` не определён как начальная, конечная или средняя масса.
  Нужна применимая методика или пояснение к 3.05.30. Пока допущение следует объявлять явно.
- Для прямой проверки Sharklet нужны применимые performance tables либо документированная поправка от fence.
- Для происхождения калибровочных графиков полезен **Airbus AC A320 Rev 44, June 2024**:
  полученный `2369.pdf` относится к May 2017. См. [обзор AC/ACAP](AC_SOURCE_REVIEW.md) и [каталог](../data/ac/source-catalog.json).

Повторно искать ACAP 757 Rev H (2024), Classic Rev E (2023), MAX Rev K (2025) и AC A321 (2026) не нужно:
эти документы уже получены. Смешанная комплектация 737-300 — отдельная ошибка выбора данных;
согласованные B1/B2 колонки есть в нынешнем ACAP. Обозначение FCOM `CFM56-3_22K` само по себе не доказывает суффикс -3B2.

Для нового источника достаточно **обложки/редакции, effectivity, целевых таблиц и их General/Conditions/Notes**.
Нужны полные шапки и единицы, FF одного двигателя или всего самолёта, границы фаз и определение опорной массы.
Для весов — состав OEW/BOW и оборудования. Эти страницы полезнее ещё одной большой книги без установленной применимости.

## Что делаем дальше

Следующий отдельный шаг — проверка выполнимости миссии. Достижение заданной дистанции,
лимиты массы/топлива и достаточность резервов должны согласованно участвовать в статусе результата;
удельный расход нельзя делить на запрошенную дистанцию, если самолёт её не пролетел.
Проверяем обычную, короткую и заведомо недостижимую миссии и граничные ограничения.

После этого подключаем подтверждённые фазы A320 с их границами и массами. Набор CES начинается
от brake release и уже включает взлёт; normal descent заканчивается на 1500 ft и не включает заход.
Нужно исключить двойной счёт, явно выбрать смысл массы снижения и определить работу с изменённым самолётом.
Лишь затем повторяем калибровку CEO и независимые проверки семейства, Boeing и FCOM.

Замечание по UI сохранено для отдельного шага: включена опция «гондолы под крылом», а двигатель
«поднят на максимум». На присланном скриншоте виден дефект геометрии; его воспроизведение и причина требуют отдельной проверки.
