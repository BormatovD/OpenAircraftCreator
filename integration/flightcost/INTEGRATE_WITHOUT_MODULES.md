# FlightCost: direct browser integration without JavaScript modules

Place **`flightcost-embed.nomodule.js`** in the FlightCost application's EXISTING static assets and include it as a normal `<script defer>` on supported server-rendered type pages. No `type="module"`, package manager, framework, or separate server service is required.

**Actual FlightCost files, workspace route, and CSRF scheme must be inspected before wiring the persistence callback.** The sample deliberately avoids inventing an HTTP endpoint.

```html
<!-- Add using the existing FlightCost static-asset helper; path is illustrative. -->
<script defer src="/static/flightcost-embed.nomodule.js"></script>
<div id="aircraft-designer-container"></div>
<script>
  document.addEventListener('DOMContentLoaded', function () {
    // Render this configuration from the SAME record that feeds the card's economics.
    // Example for 757-200 ONLY: 225-seat layout with a real RB211 engine.
    window.AircraftDesignerFlightCost.mount({
      container: document.querySelector('#aircraft-designer-container'),
      icao: 'B752',
      engine: 'RB211-535E4',
      aircraftId: 'b757-200-rb',
      layoutId: 'b752-225',
      supportedEngines: ['RB211-535E4', 'PW2037'],
      // REQUIRED BEFORE ENABLING SAVE: invoke FlightCost's real owner-scoped,
      // CSRF-protected workspace writer. Must return {id:'stored-workspace-record'}.
      // saveDesign: async function (design) { return await existingFlightCostWorkspaceSave(design); },
      // onSaved: function (saved) { /* use existing calculator navigation API */ }
    });
  });
</script>
```

**Tu-214 identifier mapping:** FlightCost uses ICAO `T204` for Tu-214, not `T214`. The catalog's canonical `icao` is `T204`; designer engine name is `ПС-90А`, with the same-engine alias `PS-90A`. On FlightCost pass `icao: 'T204'` and `engine: 'ПС-90А'`; `aircraftId` may be `tu214-ps90a` or `tu214-ps90a-factory` and `weightProfile` must match the intended model.

**Do not confuse layout categories:** A320neo 194 and A321neo 244 are **not** the A320ceo or A321ceo standard preset. For B752, the 186 / 225 / 239-seat choices are distinct layouts; the public 239-seat economics example does not prove 239 is the default used in the user's current calculator.

The adapter accepts only a `DESIGN_EXPORT` from `https://aircraft-designer.app` and the current frame, checks exact ICAO, engine, seat zones and mass limits, then delegates persistence to `saveDesign`. It acknowledges **success only after the callback returns an ID**. Every numerical field requires fresh validation server-side before storing a guest-owned custom type. Do not modify FlightCost's public aircraft database or use the Designer's weights as a fuel-flow model.

Stage-2 acceptance criteria on real FlightCost source:

1. Exact layout and engine are derived from the type page or selected calculator configuration; show an error if no matching Designer model exists.
2. `saveDesign` invokes the existing workspace write path with the same CSRF/ownership checks as normal user saves. A rejected/stale session produces `saved:false`.
3. Save returns a persisted workspace identifier. A calculator route is generated by the actual FlightCost routing layer, not by string-concatenating an assumed `USER:<id>` syntax.
4. Reopened custom type has the same stored cabin seat sum, OEW, MTOW, MLW and MZFW; LF, passengers and seat-based economics derive from **stored seats**, not public maximum.
5. Fuel burn and range either reuse an applicable, explicitly labelled FlightCost method, or show unavailable. No implied similarity of PW1127G-JM and LEAP-1A.
6. Test three languages, guest isolation, CSRF, replays, wrong-origin messages, wrong engine, failed writes, updated source-data deployments, and real URLs.
